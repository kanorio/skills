Docs/Getting started

Quickstart

Connect a repository, upload your first report and see flake rates in about five minutes.

Install the CLI

The CLI is a single binary. Run it with npx, or install it once on your runners.

npx plinth init
curl -fsSL https://get.plinth.example/install.sh | sh
plinth init

plinth init asks for a project token, writes plinth.yml and prints the step to add to your pipeline.

Upload reports

Add one step after your tests. Run it even when tests fail, or Plinth only sees the green runs.

ci.yml
- name: Upload test reports
  if: always()
  run: npx plinth upload "reports/**/*.xml"

Plinth stores test names, durations and failure messages. It never reads your source code, environment variables or build artifacts.

Flake rate

A test is flaky when it passes and fails on the same commit. Its flake rate is the share of its last 50 runs on a branch that failed and then passed without a code change.

  • Runner failures, such as lost connections or out-of-memory kills, do not count.
  • Each branch has its own rate, so experiments on a feature branch never affect main.

Quarantine

A quarantined test still runs and still reports. Its failures are marked as known and no longer fail the pipeline. Quarantine is off until you turn it on for a branch.

Test splitting

Pass the shard count and index, and Plinth prints the files that shard should run, balanced by recorded duration.

CLI reference

CommandWhat it does
plinth initCreates plinth.yml and stores the project token.
plinth upload <glob>Uploads report files. Add --shard when running in parallel.
plinth splitPrints the test files for one shard. Needs --shards and --index.
plinth quarantine lsLists quarantined tests on the current branch.

Config file

plinth.yml
project: storefront
reports: "reports/**/*.xml"
quarantine:
  branches: [main]
  threshold: 0.05   # flake rate over the last 50 runs
  never: ["payments/**"]
split:
  shards: 4

REST API

Every request uses a bearer token from your workspace settings. Responses are JSON and paginated with a cursor.

GET /v2/tests
curl https://api.plinth.example/v2/tests?status=flaky \
  -H "Authorization: Bearer $PLINTH_TOKEN"

How we cut a 40-minute suite to 7 without deleting a test

TWTheo Ward
Engineer, CI platform

Our end-to-end suite had grown to 1,284 tests. Split four ways by file count, it took 40 minutes on a bad day, because one shard always drew the checkout tests and ran for three times as long as the others.

File counts lie

Splitting by file count assumes every file costs the same. Ours ranged from 2 seconds to 2 minutes 41 seconds. The pipeline waits for the slowest shard, so the other three sat idle for most of the run.

Split by the clock

Plinth already had the duration of every test from the reports we upload. Splitting became a packing problem: put the longest files first, each into the shard with the least work so far.

split.ts
for (const file of files.sort(byDurationDesc)) {
  const shard = shards.reduce(leastLoaded);
  shard.files.push(file);
  shard.total += file.duration;
}

The fastest test is the one that never waits for another shard.

What changed

  • Median pipeline time went from 26 minutes to 7.
  • The slowest and fastest shards now finish within 8 seconds of each other.
  • Nobody deleted, skipped or rewrote a test.

If you want to try it on your own suite, the splitting guide takes about five minutes.
